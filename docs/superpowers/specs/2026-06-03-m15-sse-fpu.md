# M15 — SSE2/FPU 启用（JS 引擎前置）

## 动机
M16 计划接入 QuickJS 执行网页 JavaScript。JS 的 `number` 是 IEEE-754 `double`，
而 x86-64 System V ABI 用 XMM 寄存器传递 `float/double`——这正是内核此前全程
`-mno-sse -mno-sse2` 整数化的根因。要写 JS 引擎，必须先真正打开 SSE2/FPU，并在
抢占式调度下保证浮点寄存器状态不被破坏。

## 范围
- **内核 + 用户态都启用 FP**（不仅用户态）。代价：内核 C 代码也会改写 XMM，
  因此每个中断入口都需保存/恢复 FP 状态。
- 不引入 lazy-FP（不使用 CR0.TS / #NM 懒加载），全程 eager FXSAVE/FXRSTOR。
- **不改**已验证的整数算法（如 `kernel/raster.c` 8.8 定点光栅器）；算法现代化
  另立里程碑。

## 设计
1. **启动开 SSE**（`boot/long.asm`，`call kernel_main` 前）：清 CR0.EM、置 CR0.MP
   /CR0.NE；置 CR4.OSFXSR/OSXMMEXCPT；`fninit` + `ldmxcsr 0x1F80`。
2. **编译开关**（`Makefile`）：内核 `CFLAGS` 与用户 `UCFLAGS` 均把
   `-mno-sse -mno-sse2` 换为 `-msse -msse2`；保留 `-mno-red-zone`。
3. **中断公共路径**（`boot/isr.asm` `isr_common`）：调用 `interrupt_handler`
   前 `fxsave`、后 `fxrstor`，FP 状态存于被打断线程的内核栈。
   - 协作式切换（`context_switch`）无需处理：SysV 下 XMM 全 caller-saved，
     编译器已在调用前溢出活跃 XMM。
   - 抢占（时钟）/syscall（int 0x80，亦走 `isr_common`）/嵌套中断均由此覆盖。
   - 栈布局：GPR 帧下方对齐出 `[rsp]=regs* slot(8B)` + `[rsp+16]=FXSAVE(512B)`；
     `sub rsp,528; and rsp,-16` 保证 16 字节对齐。

## 正确性论证
被打断线程的真实 XMM 在进入 `interrupt_handler`（首个可能用 SSE 的 C 代码）之前
就被 `fxsave` 捕获；无论中途是否切换线程、是否被别的线程改写 XMM，等本线程的中断
帧最终 `iretq` 时 `fxrstor` 都会还原。新建线程首次经 `context_switch` 进入（非中断
返回），沿用启动时 `fninit` 的干净全局 FP/MXCSR 即可。

## 验证
1. `make test` 仍输出 `AETHER_BOOT_OK`。
2. `objdump -d` 内核/用户 `.o` 出现 `movsd/addsd/mulsd` 等 SSE 指令。
3. 内核浮点烟雾测试（临时）：时钟持续中断下循环计算 `double`，结果稳定。
4. 抢占折磨测试：ring-3 浮点循环被反复抢占，校验不变量无串扰、无崩溃。

## 风险
- `isr_common` 栈布局/对齐是最易错处；嵌套中断每层 +512B 内核栈占用（32KiB 够用）。
- 内核栈 `KSTACK_SIZE=32768`、boot 栈 32KiB：FXSAVE 叠加后仍有余量。

## M16 前瞻（不在本里程碑）
QuickJS 需用户态 libm（pow/fmod/floor/sin/cos/exp/log...，SSE2 仅直给 sqrtsd）、
用户态 malloc/free + 足够堆、dtoa/snprintf、nan/inf 处理。
