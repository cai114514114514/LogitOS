# X79/C600 SMBus 与 DDR3 SPD 扩展（2026-09-11）

## 交付边界

这一支针对 X79 与 Xeon E5 v1/v2 常见的 Patsburg/C600 平台，新增 Intel
C600/X79 D31:F3 SMBus 控制器和 DDR3 SPD 只读发现。Intel 的 C600/X79
规格更新把该功能标为 `8086:1d22`；驱动还要求 PCI 类为 `0c:05`。

类号只能说明设备是 SMBus 控制器，并不规定 Intel I801 寄存器布局。因此
驱动没有泛绑所有 `0c:05` 设备，也没有把 Sandy Bridge、Ivy Bridge 或其它
PCH 的相似设备 ID 猜成兼容。X79/E5 的 CPU 指令与拓扑支持由独立 CPU
工作流验证，不由本驱动声称。

## 实现

- `c/drivers/platform/intel_c600_smbus.c` 使用 PCI BAR4 的 32-byte I/O
  窗口，只开启 PCI I/O decode，保留原有 MEM、bus-master 和相邻 Status。
- 开启 PCI I/O decode 后立即读回 Command；若固件或虚拟化层忽略该写入，
  驱动恢复原 Command 并在第一次端口访问前拒绝绑定。
- 若 BIOS 没有置 `HOSTC.HST_EN`，驱动以 8-bit PCI 配置写仅置该位并读回；
  写入未生效则恢复原 PCI Command 并拒绝绑定。`HOSTC.I2C_EN` 被明确拒绝，
  因为该模式会改变命令格式。
- 每次传输先通过 `HST_STS.INUSE` 取得硬件信号量。5 ms 取锁、35 ms
  空闲等待、35 ms 传输和 5 ms KILL 等待均同时受时间与轮询次数限制。
  驱动只终止自己已经启动的超时传输；发现预先存在的 busy 传输时不会 KILL。
- 总线上只发往 `0x50..0x57` 的 SMBus Byte Data **read**。没有任意地址 API，
  没有 Quick、Byte 或写方向命令，也不会写 SPD EEPROM。
- 先读 SPD byte 2；不是 DDR3 (`0x0b`) 的响应者立即停止读取。DDR3 模块
  才读取 byte 0..145，校验 byte 126/127 的 CRC16，并根据 byte 0 bit 7
  选择 117-byte 或 126-byte 覆盖区。
- 容量由 SDRAM density、device width、primary bus width 与 rank 数计算。
  ECC extension width 单独报告；保留原始 JEDEC manufacturer 字节、序列号和
  清理后的 part number。

启动日志的稳定诊断格式为：

```text
[dev] 0000:00:1f.3 8086:1d22 class=0c.05.00 smbus driver=c600-smbus ...
[smbus] 0000:00:1f.3 Intel C600/X79 io=0x... SPD read-only 0x50-0x57
[spd] addr=0x50 ddr3 module_mib=16384 ... crc=ok ...
[spd] modules=1 module_capacity_mib=16384 ... source=SPD-not-firmware-map
```

`module_capacity_mib` 是 SPD 所描述模块的合计容量。它不是固件内存图中的可用
RAM；两者可能因固件保留区、训练失败、memory remap 设置或坏内存而不同。

## 验证

独立构建目录：`build-x79-chipset`。

```sh
python3 tests/unit/x79_chipset_run.py \
  --build build-x79-chipset/x79-chipset/positive
python3 tests/unit/x79_chipset_run.py \
  --build build-x79-chipset/x79-chipset/negative --negative-only
make BUILD=build-x79-chipset test-x79-chipset-host
```

生产源逐寄存器模型通过 31 项检查，包括一个 16 GiB ECC RDIMM、一个使用
117-byte CRC 覆盖的 8 GiB UDIMM、CRC 损坏响应者、非 DDR3 响应者、缺席
地址、PCI 状态保留、I2C 模式拒绝、BAR/HST_EN 拒绝，以及 busy/INUSE/
自有传输超时三条恢复路径和 PCI I/O decode 写入被忽略时的端口访问前拒绝。
忽略 KILL 后永久隔离、Command 恢复无法确认后端口零访问两个专项夹具各
`1/1` 通过；串口 inventory 解析 `6/6` 通过。ASan 与 UBSan 无报告。

六个独立编译负控均只产生一个预期失败：

- 写方向注入：`FAIL: SPD transactions remain read-only`
- 固定 126-byte CRC 注入：`FAIL: byte0 bit7 selects 117-byte CRC coverage`
- 删除 KILL/清理注入：`FAIL: owned timeout is killed, cleared and bounded`
- 跳过 PCI Command 读回：`FAIL: ignored I/O-decode write is refused before BAR access`
- 跳过 KILL 结果确认：`FAIL: ignored KILL permanently quarantines without clearing or releasing ownership`
- 跳过 Command 恢复确认：`FAIL: unconfirmed PCI Command restore quarantines before all BAR I/O`

两个新增生产翻译单元还使用目标内核的 `x86_64-elf`、freestanding 参数和
`-Werror` 单独编译通过。CPU ABI 编号冲突修复后，完整目标内核与 ISO 也在
同一独立目录链接成功：

```text
build-x79-chipset/kernel.elf
  sha256 1205f48115fe24b564c2832a2902fb7c230b7bc81f88b52653ad73680355ea17
build-x79-chipset/logit.iso
  sha256 5ab2f4f066d1a76d9bac11195a07e08849bd514be58be0c8c010dd0e4de4787a
```

`kernel.elf` 的静态驱动表包含 `__drvref_c600_smbus_driver`，并保留
`c600_smbus_probe`、`c600_spd_inventory` 和 `ddr3_spd_decode` 符号。这证明
生产驱动进入目标内核；不把链接成功扩写成实体硬件运行成功。

QEMU 当前设备列表没有 `8086:1d22` C600/X79 SMBus 控制器及可挂载 DDR3
SPD 的对应模型，因此没有虚构 guest 成功。宿主模型证明生产状态机和拒绝
路径；它不证明实体主板走线、BIOS 配置或 DIMM 响应。

## 实体机首次启动检查

首次启动只需保存完整串口日志，不需要让 LogitOS 写入任何磁盘或 SPD。判断
顺序如下：

1. `[dev]` 是否出现 `8086:1d22 class=0c.05` 且绑定 `c600-smbus`。
2. `[smbus]` 是否给出有效、32-byte 对齐的 I/O base。
3. 每个实际 DIMM 是否有一条 `crc=ok`，模块容量合计是否为预期的 16384 MiB。
4. 将该合计与 `[widecheck] capacity usable=...` 分开比较；缺口需要结合固件
   内存图诊断，不能倒推为 SPD 驱动故障。
5. `read-error`、`rejected=crc`、`I2C mode refused` 或未绑定记录都保留原样，
   用来决定下一轮具体主板兼容工作。

## 已知未覆盖

- 尚未在用户的实体 X79 主板上运行。
- 不支持 DDR2/DDR4、SPD page-select、温度传感器、写保护设置或任何 SPD 写入。
- 不推断 DIMM 的物理丝印槽位、CPU channel 或 NUMA 拓扑；SPD 地址与主板槽位
  的对应关系由主板布线决定。
- 不支持 C606/C608 的额外内部 SAS SMBus 控制器，它们不是 X79 D31:F3 的
  `8086:1d22` 主机接口。
