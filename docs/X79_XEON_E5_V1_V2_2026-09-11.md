# X79 / Xeon E5 v1-v2 CPU platform support

This work targets the LGA2011-0 Sandy Bridge-EP and Ivy Bridge-EP CPU path,
especially the E5-1600 and E5-2600 v1/v2 families commonly fitted to
third-party X79 boards. Intel's v1 and v2 datasheets identify the socket as
LGA2011-0. The target does not include LGA1356 E5-1400/2400 variants or
LGA2011-3 E5 v3/v4.

Socket compatibility does not establish motherboard compatibility. Intel's
X79 compatible-products page lists the supported Core i7 products and does
not list Xeon E5. A particular consumer X79 board still needs BIOS support and
the required microcode for the installed Xeon. LogitOS discovers capabilities;
it does not use a processor brand-string allowlist and cannot repair a firmware
that refuses to initialize the CPU.

## Production behavior

- The logical-CPU ceiling and all coupled per-CPU storage are 32 slots. This
  covers a single 12-core/24-thread Ivy Bridge-EP processor without the old
  silent truncation after CPU 7. `PERCPU_MAXCPU`, syscall accounting, kernel
  profiling and heap magazines use the same production ceiling. A fatal lock
  diagnostic prints complete two-digit CPU indices.
- Early CPUID inventory decodes display family/model/stepping, CPUID leaf 0B
  topology and x2APIC identifiers, deterministic cache leaf 4, invariant-TSC
  capability, APIC mode and MCA bank capabilities. Leaf 1 plus leaf 4 is a
  checked fallback for absent or malformed leaf 0B. Cache-size multiplication
  rejects overflow. Family 6/model `0x2d` and `0x3e` add diagnostic
  labels only; feature decisions remain capability based.
- MCA support is passive inventory. It reads `IA32_MCG_CAP` only when CPUID
  reports MSR, MCE and MCA. This change does not enable CR4.MCE, program banks
  or claim machine-check recovery.
- The existing clock code calibrates TSC against PIT, checks skew and falls
  back when needed. The new report separately records the invariant-TSC bit;
  it does not assume that bit is present.
- The kernel's context and interrupt ABI remains FXSAVE/FXRSTOR. BSP and AP
  boot paths explicitly clear CR4.OSXSAVE, and the report distinguishes AVX
  hardware (`avx_hw`) from OS-usable AVX (`avx_os`). AVX is unavailable until
  a future XSAVE context switch and interrupt ABI is implemented.
- `SYS_CPU_COUNT` is ABI number 196, after an all-header collision scan. It
  returns the runtime `smp_cpu_count()` without changing the zero-argument
  `SYS_CPU_INDEX` contract. mini-libc uses it for
  `_SC_NPROCESSORS_ONLN`; the opt-in agent worker policy permits this read-only
  query.
- The APIC integration accepts enabled MADT type 0 and type 9 CPU entries and
  keeps 32-bit APIC IDs. An ordinary image preserves the firmware's xAPIC or
  x2APIC mode. It does not enable x2APIC itself because interrupt remapping is
  not implemented. The x2APIC backend and its separate acceptance suite are
  owned by the firmware/APIC workstream; the Xeon runs below exercised xAPIC.

## Executed verification

`tests/xeon_e5.mk` is the stable fragment. Its host gate runs source controls
before positive fixtures. The QEMU CPU names ending in `-v1` are QEMU model
versions and do not prove Xeon generation. Each guest therefore hard-asserts
the CPU signature actually printed by LogitOS. These are synthetic CPUID
profiles, not physical processor identities.

| Gate | Observed result | Evidence |
|---|---|---|
| Pure CPUID/MSR decoder | 45 checks, zero failures for synthetic Sandy Bridge-EP 8C/16T and Ivy Bridge-EP 12C/24T, fallback and malformed inputs | `build-x79-e5-hostgate/xeon-e5-platform-test` |
| CPUID topology negative control | First `top->leaf_b` decision was changed with a verified Python one-shot replacement; the fixture failed | `build-x79-e5-hostgate/xeon-e5-control/platform-negctl.log` |
| High-CPU fatal diagnostic | Host fixture observed `cpu 30 released a lock held by 31`; three-bit truncation control was rejected | `build-x79-e5-hostgate/xeon-e5-lock-diag-test` |
| BIOS, 16 GiB, synthetic family 6/model 0x2d, 16 threads | Reported 8C/16T from leaf 0B, brought 16/16 CPUs online, passed SIMD-under-interrupt self-test, returned sysconf=16 and completed 12 concurrent ring-3 workers | `build-x79-xeon/xeon-e5-runs/bios-16/` |
| UEFI, 16 GiB, synthetic family 6/model 0x3e, 24 threads | Reported 12C/24T, brought 24/24 CPUs online, passed the same interrupt/ring-3 gates and returned sysconf=24 | `build-x79-xeon/xeon-e5-runs/uefi-24/` |
| Restored 8-slot control | On a 24-thread guest, only 8/24 came online and sysconf returned 8; the positive contract failed | `build-x79-xeon/xeon-e5-runs/cap-neg/` |
| Inherited-OSXSAVE control | Forced `osxsave=1` was detected while `avx_os=0`; 16/16 CPUs and the FXSAVE SIMD interrupt path still passed | `build-x79-xeon/xeon-e5-runs/osxsave-neg/` |

The production 32-slot kernel has a 13,324,288-byte `.bss`, compared with
12,775,424 bytes in the otherwise equivalent 8-slot control: **548,864 bytes**
of load-time zero-fill. Of that, 393,216 bytes are the 24 additional 16 KiB
syscall stacks. Runtime ELF file size increased by 15,632 bytes in the measured
build; `.bss` itself does not occupy file payload. `test-xeon-e5-size` parses
ELF64 sections directly and rejects a BSS delta below the required stacks or
above 1 MiB.

The ring-3 probe uses twelve simultaneous workers. A guarded pthread stack
uses two VMA records and the current per-process `VMA_MAXAREA=32` layout runs
out around fourteen workers, before the 64-thread process table. The probe
therefore proves execution beyond the old eight-CPU boundary without claiming
one permanently resident pthread for every online CPU.

Reproduction:

```sh
make BUILD=build-x79-xeon test-xeon-e5-host
make BUILD=build-x79-xeon test-xeon-e5-bios
make BUILD=build-x79-xeon test-xeon-e5-uefi
make BUILD=build-x79-xeon test-xeon-e5-cap-control
make BUILD=build-x79-xeon test-xeon-e5-osxsave-control
make BUILD=build-x79-xeon test-xeon-e5-size
```

## Verification boundary

No physical X79 board or Xeon E5 has been booted in this run. QEMU proves the
high-thread kernel, ABI, boot and ring-3 paths under observed model signatures;
the deterministic fixture proves the decoder for those signatures. It does
not prove a board BIOS, microcode package, DDR3 training, a real MCA event,
turbo/power management, NUMA/QPI, or an actual x2APIC firmware handoff.

Sixteen GiB DDR3 needs no CPU-brand driver in the OS. Firmware trains DRAM and
publishes the usable map; chipset SMBus/SPD inventory is covered by the
separate X79/C600 workstream. Dual-socket E5-2600 systems, hotplug-only MADT
CPUs, E5 v3/v4, and per-SKU performance or power behavior are outside this
acceptance claim.
