# Intel Core i7-14700KF CPU 适配审计与实体机验收规范

日期：2026-09-13

范围：CPU、SMP 拓扑、x2APIC、UEFI 页表模式交接、扩展状态、TSC、微码与调度提示。主板、内存、GPU、存储和网络不在本文范围内。

证据边界：本文依据 Intel 官方资料和 LogitOS 源码审计制定验收条件；尚未在用户的 14700KF 实体机上执行，因此不能把 host fixture 或 QEMU 结果表述为“14700KF 已实机支持”。

## 结论与优先级

14700KF 不是一个“多加几个 CPU 槽位”就能正确工作的同构 SMP。它有 8 个带 SMT 的 P-core、12 个不带 SMT 的 E-core，共 20 核 28 线程。LogitOS 的首个实体机目标应是正确且保守地使用全部 28 个逻辑处理器；Thread Director/HFI、AVX 和运行时微码更新均不得成为启动前置条件。

| 优先级 | 合同 | 最终达标条件 |
| --- | --- | --- |
| P0 | UEFI 5-level paging 降级 | 从合法的 LA57=1 来态也能按 Intel 顺序退出 IA-32e，并在装入 LogitOS PML4 前确认 CR4.LA57=0；顺序和漏清均有会变红的负控 |
| P0 | 混合拓扑 | MADT 枚举 28 个启用 LP；在每个 LP 上采样 CPUID.1A 与 1F/0B；汇总为 16 P 线程、12 E 线程、20 核、1 package |
| P0 | x2APIC 与 AP 启动 | 保留完整 32 位 x2APIC ID；全部 28 LP 上线且每个 LP 都收到时钟中断和 IPI；不能依赖回退到 xAPIC |
| P0 | 扩展状态 ABI | BSP/AP 均明确清 CR4.OSXSAVE；继续只用 FXSAVE/FXRSTOR；内核和用户程序不得生成或执行 AVX 指令 |
| P0 | 时间正确性 | 只在 CPUID 声明 invariant TSC 或经过验证的虚拟机政策下使用 TSC；当前虚拟机例外尚未做到 VMM 识别或白名单，实体机跨 P/E 核迁移还须证明无倒退并测量原始偏差 |
| P1 | 微码与缓解能力盘点 | 读取每个 LP 的微码版本，重新枚举缓解能力并如实报告；首轮依赖已更新 BIOS 加载微码；当前尚未实现 |
| P1 | Thread Director/HFI | 只枚举和报告，不由当前内核配置；等内存所有权、中断、生命周期与调度策略完成后再启用 |

## 当前实现状态与本轮证据

当前生产树已经接入以下 CPU 路径，但这些结果仍是源码、host fixture 和 QEMU 证据，不是 14700KF 实机证明：

- `c/kernel/cpu/cpu_platform.c`、`cpu_platform.h`：以 family/model/stepping 只做 Raptor Lake-S 诊断标签；能力检测不依赖型号白名单。实现了严格的 CPUID.1F 解析、0B 回退、逐 LP 的 CPUID.1A core type、完整 32 位 x2APIC ID、cache/TSC/xstate/APIC/MCA inventory。hybrid CPU 缺少可信 1F/0B 时会把物理拓扑标为 unknown，不再用 legacy SMT 公式伪造 core identity。
- `c/kernel/cpu/smp.c`、`smp_topology.c`：每个上线 LP 自己采样 CPUID，并与 MADT APIC ID 连接；ID 不一致时保留逻辑 CPU 在线，同时把该记录隔离为 unknown。汇总按 `(package_id, core_id)` 去重并分别统计 P/E/unknown。调度策略仍是 `uniform-online-cpus`，没有 Thread Director/HFI 权重。
- `c/boot/efi/trampoline.S`、`c/boot/boot.asm`、`c/boot/ap_trampoline.asm`：生产启动路径已加入 PCIDE/PG/LME/LA57 顺序门及 BSP/AP 的四级页表约束。现有可执行 seam 只在 PG/LME 已关闭后强制 LA57；活跃 PML5 来态仍未覆盖。
- CPUID.6 的 HFI/Thread Director capability、capability bitmap、table pages、当前 LP row 和 class 数量已接入只读 inventory。启动报告只显示当时执行 `platform_report` 的 LP；SMP 拓扑记录目前不持久化每个 LP 的 HFI row。内核没有读写 `IA32_HW_FEEDBACK_PTR`、`IA32_HW_FEEDBACK_CONFIG` 或逐 LP 的 `IA32_HW_FEEDBACK_THREAD_CONFIG`，也没有 HFI 中断或调度消费端；这只能说明 LogitOS 没有主动配置 HFI/Thread Director，不能证明固件来态为关闭。
- 当前没有 `IA32_BIOS_SIGN_ID` 微码 revision 读取、运行时微码 loader、安全缓解能力汇总或缓解策略。它们是本规范的 P1 待办，不能从 HFI fixture、CPU 型号标签或 BIOS 已更新的假设推出。

## 1. Intel 官方硬件合同

Intel 的 14700KF 产品页给出的固定 SKU 目标是：

- 20 核：8 P-core + 12 E-core。
- 28 线程：P-core 有 SMT，E-core 无 SMT，所以应看到 16 个 P 逻辑处理器和 12 个 E 逻辑处理器。
- 单路 FCLGA1700，AVX2，Intel Thread Director，最大 Turbo 5.6 GHz。
- DDR5-5600 或 DDR4-3200 是内存控制器规格；它不改变本文的 CPU 拓扑验收。

Intel Raptor Lake-S 数据手册和安全处理器表给出的诊断身份包括：

- Raptor Lake-S / 14th Gen 的常见签名为 display family 06H、model B7H、stepping 1，即 CPUID signature `0xB0671`。
- Intel 的当前安全表也列出 hybrid Raptor Lake-S 的 06_B7H/1/B0671；另有 06_BFH stepping 2、5 的 Raptor Lake-S 条目。
- 这些值只用于诊断标签。启动、拓扑、页表、APIC、xstate 和缓解策略必须由能力位决定，不能用型号白名单决定能否启动。实体机输出的 CPUID 才是该颗 CPU 的权威值。

目标机应保存原始 CPUID/MSR 证据，而不只打印品牌字符串。最低采样集如下：

| 枚举 | 用途 |
| --- | --- |
| CPUID.0 和 CPUID.1 | vendor、最大基本叶、signature、TSC、XSAVE、OSXSAVE、AVX、x2APIC 能力 |
| CPUID.7.0 | EDX[15] hybrid；ECX[16] LA57；安全能力位 |
| CPUID.1A.0 | 当前逻辑处理器的 core type 与 native model ID |
| CPUID.1F 全部有效子叶 | 首选拓扑层级、shift 与当前 LP 的完整 x2APIC ID |
| CPUID.0B 全部有效子叶 | 仅在 1F 不存在或 1F.0:EBX=0 时回退 |
| CPUID.6.0 | HFI、Thread Director 与表结构几何信息 |
| CPUID.0D | 未来 XSAVE 区域大小和支持的 xstate；当前只记录 |
| CPUID.80000007 | EDX[8] invariant TSC |
| IA32_APIC_BASE | APIC 已启用、当前 xAPIC/x2APIC 模式；读取必须先有 MSR/APIC 能力 |
| IA32_BIOS_SIGN_ID | 实体验收所需的当前微码修订号；应按 Intel 指定的 WRMSR 0、CPUID.1、RDMSR 序列读取，当前尚未接入 |

## 2. P0：UEFI 的 CR4.LA57 交接

### 2.1 为什么是启动阻断项

LogitOS 构建的是四级页表，CR3 指向 PML4。若固件留下 CR4.LA57=1，下一次进入 IA-32e 时同一个 CR3 会被解释为 PML5 根，结果通常是在最早的内核指令附近页故障或三重故障。UEFI 启动成功且普通 OVMF 启动成功并不能证明这个来态，因为普通固件可能一直交付 LA57=0。

Intel 定义 CPUID.7.0:ECX[16] 为 LA57 能力位。是否支持必须在运行时读取；无论具体 SKU 的普通固件当前是否使用五级页表，LogitOS 的 UEFI handoff 都应对合法 LA57=1 来态有明确合同。

### 2.2 合法顺序

Intel SDM 的限制是：

- 在 64-bit mode 中清 CR0.PG 会 #GP，所以要先远跳到 `CS.L=0` 的 compatibility code segment。
- CR4.PCIDE=1 时清 CR0.PG 也会 #GP，所以 PCIDE 必须在 PG 仍为 1 时先清除并读回。
- CR4.LA57 和 CR4.PAE 在 4-level/5-level paging 正在使用时不能修改；必须先使 CR0.PG=0。
- IA32_EFER.LME 在 PG=1 时不能修改。

LogitOS 从 UEFI 进入 Multiboot2 的生产顺序应固定为：

1. `CLI`、`CLD`，并保证后续关页指令所在页是 identity mapped。
2. 仍在 64-bit mode、CR0.PG=1 时清 CR4.PCIDE，写回后再次读取 CR4 并确认 PCIDE=0。
3. 用 far transfer 进入 `CS.L=0` 的 compatibility segment；立即重载可用的数据段。
4. 清 CR0.PG；从此 IA32_EFER.LMA=0。
5. 清 IA32_EFER.LME。
6. 清 CR4.LA57、CR4.PAE、CR4.PGE，写回后重新读取 CR4 并确认 LA57=0。
7. 跳入 32 位 Multiboot2 入口。LogitOS 在装入自己的 PML4 并重新设置 PAE/LME/PG 前再次明确清 LA57。

SIPI 后的 AP 通常从复位状态开始，但 AP trampoline 仍应在装入内核 PML4 前明确清 LA57。这使 BSP 与 AP 共用同一个四级页表合同，也避免虚拟平台或未来启动路径把“复位默认值”误当成内核不变量。

### 2.3 必须保留的正控和负控

静态门必须反汇编实际生产 trampoline，而不是检查一份复制的测试实现。一个判定同时要求：

```text
PCIDE clear/write/readback
  < compatibility far jump
  < CR0.PG clear
  < IA32_EFER.LME clear
  < LA57/PAE/PGE clear/write/readback
  < kernel jump
```

至少需要三种精确变异，并且每种只因预期原因变红：

1. 删除 LA57 clear：顺序门或最终读回必须报告 `LA57 retained`。
2. 删除 LA57 的 fresh readback：静态门必须失败，不能把一次 CR4 写当成已确认状态。
3. 把 LA57 clear 移到 CR0.PG=1 的位置：静态顺序门必须失败。该变异只做反汇编负控，因为在真实 Intel CPU 上执行会 #GP。

QEMU 可执行门可在 PG/LME 已关闭后设置并读回 LA57=1，再走生产 clear/readback；跳过 clear 的变异必须在显式读回处输出唯一失败 breadcrumb 并停机。这个门能证明实际生产掩码和分支被执行，但不能证明“从正在工作的 PML5 退出”。

完整的 LA57 来态证明需要另一个引导 prelude：在 `-cpu max,+la57` 下创建 PML5，令其一个 PML5E 指向现有 identity-mapped PML4，按 Intel 顺序使 CR4.PAE=1、CR4.LA57=1、LME=1、CR3=PML5、PG=1，再进入生产 UEFI handoff。只有这条测试或真实五级页表固件，才能覆盖 compatibility jump 和 CR0.PG 清除发生在活跃 5-level paging 中的路径。普通 OVMF 和“PG 关闭后强制 LA57”的 seam 都不能替代它。

实体机串口日志应记录进入 descent 前的 `CR0.PG/CR4.PCIDE/CR4.LA57/EFER.LMA/LME`，并在 handoff 后记录 BSP 与每个 AP 的 `CR4.LA57=0`。不得在打印完状态后继续信任固件页表中的普通 C 栈；实际关页段仍应无栈运行。

## 3. P0：混合拓扑与 x2APIC

### 3.1 逐逻辑处理器采样

Intel 指定 CPUID.7.0:EDX[15] 标识 hybrid。hybrid=1 时，软件要在目标逻辑处理器上读取 CPUID.1A：EAX[31:24] 为 `0x40` 表示 Intel Core/P-core，`0x20` 表示 Intel Atom/E-core。P-core 的两个 SMT sibling 都返回 `0x40`；E-core 没有 SMT。因此 BSP 上读取一次 CPUID.1A 不能代表整个 package。

启动流程应为：

1. 从 ACPI MADT 收集 enabled/online-capable CPU，兼容 type 0 Local APIC 与 type 9 Local x2APIC，保存完整 32 位 APIC ID，并按 APIC ID 去重。
2. 为每个成功上线的 LP 建立固定 CPU slot；不得用 APIC ID 直接作为数组下标。
3. 在该 LP 自己执行 CPUID.7.0、1A、1F 或 0B，保存原始寄存器和解析结果。
4. 比较 CPUID.1F/0B:EDX 的 x2APIC ID 与 MADT ID。若不一致，CPU 可以保持在线，但 topology 必须降级为 unknown，并在汇总中显式计数，不能静默归入另一个 core。
5. 对实际采集到的 x2APIC ID 应用各层 shift/mask，按 `(package_id, core_id)` 去重得到实际物理核数，再按 core type 汇总。

14700KF 的实体机期望值是：

```text
MADT enabled logical processors = 28
online logical processors       = 28
packages                        = 1
unique physical cores           = 20
P logical / P cores             = 16 / 8
E logical / E cores             = 12 / 12
unknown logical / cores         = 0 / 0
APIC identity mismatch          = 0
```

### 3.2 CPUID.1F/0B 的严格边界

正常选择算法是：若最大基本叶至少为 1F 且 CPUID.1F.0:EBX 非零，优先使用 1F；否则若最大基本叶至少为 0B 且 CPUID.0B.0:EBX 非零，使用 0B；再否则才考虑 legacy 叶。LogitOS 还会对整组 1F 子叶做一致性校验；若 1F 广告非空但结构损坏，则只在 0B 能通过同类严格校验时回退，否则把 hybrid 物理拓扑标为 unknown。1F 是 0B 的首选超集，并可描述 Core 之外的 Module、Tile、Die 和 DieGrp 域。

解析器必须遵守这些约束：

- 1F 当前定义的 domain type 为 1..6，0 表示无效并终止后续子叶。软件不能依赖 domain type 的数值顺序；Intel 要求三域解析器把未知的非零上层 domain 吸收到下方已知 Core mask，不能忽略它，也不能仅因未来出现 7..255 的新类型就截短 package boundary。
- 1F 的子叶按由内到外排序；当前架构的 Logical Processor 与 Core 域应存在。要拒绝 APIC ID 在不同子叶变化、shift 反向、已知域重复或无限子叶。shift 只要求不下降，不能要求严格递增：Intel 明确允许 Core shift 为 0 表示单核，Logical Processor shift 也可能为 0，合法单实例相邻层可以相等。
- 0B 只描述 Logical Processor、Core 和隐含 Package，仍应用新版算法解析。
- `EDX` 是当前 LP 的完整 x2APIC ID。
- `EBX[15:0]` 是 Intel 出厂配置的 addressable/diagnostic 数，不是 BIOS/OS 实际可见处理器枚举值。Intel 明确写明软件不得用它枚举系统拓扑。

因此，若结构字段仍名为 `logical_per_package`，输出必须标为 `cpuid-addressable` 或 `diagnostic`；它不能与 MADT/online count 混用，也不能用于宣称“28 个线程已上线”。实际值只能来自 MADT 列表和逐 LP 采样。

### 3.3 x2APIC

CPUID.1:ECX[21] 只表示硬件支持 x2APIC，不能证明当前已处于 x2APIC mode。当前模式由 IA32_APIC_BASE 的 enable/EXTD 位决定。现代固件还可能锁住从 x2APIC 回退的路径，因此内核必须能在固件已有的 x2APIC mode 下工作，不能以“切回 xAPIC”作为兼容方案。

验收至少覆盖：

- MADT type 9 的大于 255 的 ID 不截断、不碰撞。
- x2APIC MSR 模式的 EOI、ICR、LVT timer 与错误状态路径。
- BSP 对每个 AP 的 INIT/SIPI/等待超时；失败 CPU 有明确 ID 和阶段。
- 每 CPU 定时器中断计数增长。
- BSP 到全部 AP、全部 AP 到 BSP 的 IPI round trip；再执行全互发压力。
- 28 LP 同时进入调度压力时无锁死、无重复 CPU slot、无越界。

当前 `ACPI_MAX_CPUS=32` 与正常构建的 `PERCPU_MAXCPU=32` 足够容纳 14700KF 的 28 LP；仍需从最终普通 ELF 或实体日志证明没有负控的 8-CPU 上限混入产物。

## 4. P0：XSAVE/AVX 政策

14700KF 产品页声明 AVX2。硬件支持不等于 LogitOS 可以启用：当前中断和 signal ABI 保存的是 512-byte FXSAVE image，只覆盖 x87 与 XMM，不覆盖 YMM 上半部。只设置 CR4.OSXSAVE/XCR0 而不迁移所有保存路径，会造成中断时静默数据损坏。

本轮正确策略是：

- BSP 和每个 AP 的启动汇编都明确写 CR4 清 OSXSAVE；后续 CPUID/platform report 可观察状态，但 CR4 写入之后没有紧邻的读回分支或硬拒绝门，当前也没有逐 AP 的 xstate 报告。
- 只启用 OSFXSR/OSXMMEXCPT，继续使用 FXSAVE/FXRSTOR。
- 记录 CPUID.0D 几何，但不据此启用 AVX。
- 将 CPUID.1 的 AVX 位报告为 `avx_hw`，同时单列 `avx_os=0`、`osxsave=0`、`xcr0=0` 和 `abi=fxsave`，避免硬件能力被误解为用户态可执行。
- 保持内核与 ring-3 编译选项在 SSE/SSE2 基线，禁止 `-mavx*`。

正控应在高频 timer、syscall、signal 与跨 CPU 调度下反复保存/恢复 XMM 状态。当前源码负控通过删改 BSP/AP 的 OSXSAVE clear 让静态政策检查变红；现有可执行 inherited-OSXSAVE 负控则在报告观察到 `osxsave=1` 后仍继续完成 SMP 和 ring-3，因此它证明的是违规状态可被诊断，不是启动已硬拒绝。未来若加入紧邻 CR4 写入的读回硬门，负控才应验证在进入 ring-3 前停机。另一类负控是删掉 interrupt FXSAVE/FXRSTOR，XMM canary 必须变红。若要启用 AVX，需要单独完成 CPUID.0D/XCR0 policy、64-byte 对齐的动态 XSAVE area、全部 interrupt/trap/signal/context-switch/coredump ABI 迁移及 YMM 压力负控。

## 5. P0：Invariant TSC 与跨 P/E 核时间

是否可把 TSC 当系统时钟由 CPUID.80000007:EDX[8] 决定，不能由 Raptor Lake 品牌名推断。`c/kernel/core/ktime.c` 当前实际条件是 `invariant || hypervisor`：只要 CPUID.1:ECX[31] 为 1 就接受 TSC，并未识别、验证或白名单化具体 VMM。因此“受控虚拟机政策”是虚拟机侧仍须收紧的目标，不是当前实现事实。该缺口不改变无 hypervisor 位且 invariant-TSC=1 的实体 14700KF 路径，但这两个来态以及跨 P/E 核行为仍必须由实体日志证明。QEMU `max` 不声明 invariant TSC，它只能覆盖当前宽松的 hypervisor 分支，不能替代实体机证据。

14700KF 实体验收要同时测试公开时钟和原始计数器：

1. 记录每个 LP 的 invariant 位，检查平台域能力一致。
2. 用同步 IPI 屏障在全部 P/E LP 上采样原始 TSC，记录最大 pairwise offset；不要只看带 cross-core clamp 的 monotonic API，因为 clamp 会隐藏未同步的 TSC。
3. 将单个线程在 P-core sibling、不同 P-core、E-core 与 P/E 之间迁移，至少持续数分钟读取 monotonic clock；倒退次数必须为 0。
4. 同时进入 idle、满载和频率变化，检查 PIT/RTC 校准与 monotonic 速率不漂移。
5. 对 timer deadline、sleep 和超时执行压力，确认没有瞬时巨大增量或全部 deadline 一起过期。

QEMU 只能证明 hypervisor 分支、换算、wrap 与 synthetic migration 逻辑；不能证明实体硅上的跨核同步、主板时钟、深 C-state 或频率切换。

## 6. P1：微码与安全缓解边界（当前未实现）

Intel 说明 BIOS/UEFI 通常在启动阶段加载微码。当前 LogitOS 没有读取 `IA32_BIOS_SIGN_ID`，也没有运行时微码 loader；首轮实体测试必须先升级主板 BIOS，并把“内核只读记录每个 LP 的微码版本”保留为尚未完成的验收项。最低 revision 必须在部署时重新查询 Intel 当前表，不能把本文日期对应的表值编译成永久型号启动门。

Intel 指定的版本读取顺序是：

```text
WRMSR IA32_BIOS_SIGN_ID (0x8B) = 0
CPUID EAX=1
RDMSR IA32_BIOS_SIGN_ID
revision = high 32 bits
```

后续实现应在每个 LP 上记录结果，并枚举至少以下安全能力：CPUID.7.0:EDX 的 MD_CLEAR[10]、IBRS/IBPB[26]、STIBP[27]、L1D_FLUSH[28]、IA32_ARCH_CAPABILITIES[29]、SSBD[31]；只有 [29]=1 才能读 IA32_ARCH_CAPABILITIES 0x10A。所有 SPEC_CTRL、PRED_CMD 或 ARCH_CAP 访问都必须由对应枚举位保护。当前生产树尚未提供这组枚举或策略。

“打印这些位”不等于已完成缓解。LogitOS 已运行不可信 ring-3 代码时，若还没有在用户/内核或进程边界实施所需策略，报告必须明确写 `enumerated, mitigation policy not enforced`，不能写“安全已支持”。

运行时微码 loader 不应塞进首轮 bring-up。Intel 的 2025 Runtime Microcode Update 规范要求所有 LP rendezvous，按 update scope 选择 initiating LP，校验 header/platform/checksum/minimum runtime revision，其他 LP 用受限 spin loop 等待，全部 LP 验证新 revision，并重新检查可能变化的 CPUID 与 architectural MSR。缺少其中任一部分时，依赖 BIOS 微码比一个不完整的 kernel loader 更可靠。

## 7. P1：Thread Director 与 HFI 边界（只读 inventory 已实现）

Intel Thread Director 是调度优化提示，不是识别 P/E 核或启动全部核心的前置条件。静态 core type 来自逐 LP 的 CPUID.1A；即使 HFI/Thread Director 不启用，内核也必须能公平地调度 28 LP。

当前只读 inventory 记录：

- CPUID.6:EAX[19]：HFI。
- CPUID.6:EAX[23]：Intel Thread Director。
- CPUID.6:EDX[7:0]：capability bitmap；当前记录 performance 与 energy-efficiency 两位。
- CPUID.6:EDX[11:8]：HFI/Thread Director table 大小，编码为减一后的 4 KiB page 数；实现保存解码后的 `field + 1`。
- CPUID.6:EDX[31:16]：当前 LP 在表中的索引，必须逐 LP 采样。
- CPUID.6:ECX[15:8]：Thread Director class 数量；只有 Thread Director capability 存在时才采信。

当前实现既不读也不写 IA32_HW_FEEDBACK_CONFIG、IA32_HW_FEEDBACK_PTR 或逐 LP 的 IA32_HW_FEEDBACK_THREAD_CONFIG；这只能证明 LogitOS 没有主动配置 HFI/Thread Director，不能证明固件来态一定关闭。后续真正启用至少需要：

1. 按 CPUID 给出的大小分配并清零 package-scoped 物理内存，保证生命周期和缓存属性正确。
2. 写 IA32_HW_FEEDBACK_PTR 0x17D0 后才可设置 IA32_HW_FEEDBACK_CONFIG 0x17D1。
3. HFI 用 bit 0；Thread Director 要求 bit 0 和 bit 1 同时为 1，且 bit 1 只有 CPUID.6:EAX[23]=1 时合法，否则 #GP。
4. 启用 Thread Director 时，还要在每个目标 LP 写 `IA32_HW_FEEDBACK_THREAD_CONFIG` 0x17D4 bit 0；读取 `IA32_THREAD_FEEDBACK_CHAR` 0x17D2 时检查 valid 位再使用 class ID。
5. 处理 IA32_PACKAGE_THERM_STATUS[26] ready/change 与 IA32_PACKAGE_THERM_INTERRUPT[25] 通知。
6. 关闭 package config bit 0 后等待 hardware acknowledgement，再回收硬件仍可能写入的表内存。
7. 明确 INIT/SIPI 生命周期：package 的 PTR/CONFIG 跨 INIT 保留，而逐 LP 的 0x17D4 bit 0 会被清零；恢复时只按已观察到的实际状态重建配置。
8. 调度器要定义能力值陈旧、未知 class、任务迁移、公平性和退化行为，并有性能与功耗基线。

在这些条件完成前，可把 P/E 类型显示给诊断层，但不要宣称“Thread Director 已适配”，也不要让缺少 HFI 数据导致 CPU 下线或任务饥饿。

## 8. QEMU 能证明什么

本机是 arm64，Homebrew QEMU 11.0.0 只有 TCG。`max` CPU 模型可提供 `la57=true`、`x2apic=true`、`xsave=true`、`avx=true`，但 `invtsc=false`，且没有一个真实的 14700KF/Raptor Lake 混合 CPU 模型。`max` 默认也不是 Intel vendor 的 P/E 异构拓扑。

| 测试 | 可以证明 | 不能证明 |
| --- | --- | --- |
| host CPUID fixture | 1F 优先、0B 回退、1A 类型、malformed leaf、model label、HFI capability/geometry gating、EBX 不用于实际 core count | 14700KF 真实返回值、固件过滤和每 LP 差异 |
| 28-vCPU QEMU | 数组上限、MADT 数量、AP 启动、timer/IPI 的软件路径 | 8P/12E、真实 P/E SMT 差异、功耗和 turbo |
| x2APIC synthetic guest | MSR 访问、宽 ID 和路由软件路径 | 主板 MADT、固件 lock、真实 I/O APIC/中断布线 |
| LA57 PG-off force seam | 生产 clear/readback 的实际执行与 skip-clear 负控 | 从活跃 PML5 teardown、真实 #GP 模型 |
| 未来 PML5 prelude（尚未实现） | 完成后可覆盖活跃 5-level paging 到生产 handoff 的完整指令路径 | 当前没有执行证据；完成后仍不能代表具体主板 UEFI 的来态和固件 bug |
| OSXSAVE/FXSAVE 检查 | BSP/AP 显式清位的生产指令、静态变异检测与后续 BSP 诊断 | 紧邻 CR4 写入的硬拒绝读回、逐 AP xstate 报告、未来 XSAVE/AVX 迁移、真实长期硅稳定性 |
| HFI host fixture | CPUID.6 capability、geometry、class 与缺失 capability 时的清零策略 | MSR 配置、反馈质量、硬件表更新、中断时序 |
| 微码与安全缓解 | 当前无实现或 fixture | 微码 revision、BIOS 加载结果、缓解能力与策略均未验证 |

QEMU TCG 对某些控制寄存器非法顺序未必产生与 Intel 硅一致的 #GP。因此 LA57/PCIDE 结论必须同时有生产对象反汇编顺序门和显式寄存器读回，不能只以“虚拟机没崩”为证据。

## 9. 建议门禁和实体机采集

共享树冻结后，用独立输出目录执行已有或正在接入的目标：

```sh
make BUILD=build-14700kf-audit test-raptor-lake-host
make BUILD=build-14700kf-audit test-raptor-smp-host
make BUILD=build-14700kf-audit test-uefi-la57-host
make BUILD=build-14700kf-audit test-uefi-la57
make BUILD=build-14700kf-audit test-x2apic-host
make BUILD=build-14700kf-audit test-xeon-e5-host
```

若执行 synthetic guest，必须用另一个 BUILD，并保存完整命令、QEMU 版本、CPU 属性、串口日志与结构化结果。测试宏产物不能作为普通发布内核或 ESP：

```sh
make BUILD=build-14700kf-qemu \
  X2APICVERIFY=1 RAPTORSMPVERIFY=1 \
  test-raptor-smp-synthetic-guest
```

实体机至少执行 10 次断电冷启动和 20 次 warm reboot。每次保存：

- BIOS 版本与设置、CPUID signature；实现微码 reader 后再由 LogitOS 记录每 LP revision，当前不能从内核日志获得该项。
- UEFI descent 前后 PCIDE/LA57/PAE/LME 状态和 breadcrumb。
- MADT 原始 type 0/type 9 项、逐 LP CPUID 原始值、完整 x2APIC ID。
- 28/28 online、20 core、16/8 P、12/12 E 的结构化汇总。
- 每 LP timer 中断、IPI round trip、AP 启动时长与失败阶段。
- 原始 TSC offset、跨 P/E 迁移 monotonic 结果、PIT/RTC 校准。
- OSXSAVE=0、XCR0 未访问、XMM canary 压力结果。
- HFI/Thread Director 只读 CPUID inventory；当前内核没有 config MSR 读回或写入，因此实体日志不得臆测固件来态。
- 28 worker 的调度/锁/内存压力，无 hang、panic、CPU slot 重复或越界。

只有上述实体证据通过，才可以写“LogitOS 在这台 i7-14700KF 机器上支持全部 20 核 28 线程”。host 测试、QEMU 28 vCPU、成功编译和普通 OVMF 启动分别只证明它们实际覆盖的边界。

## 10. 源码审计关注点

本次审计对应的主要生产路径为：

- `c/boot/efi/trampoline.S`、`c/boot/boot.asm`、`c/boot/ap_trampoline.asm`：PCIDE/LA57/PAE/LME 与 BSP/AP xstate 合同。
- `c/kernel/cpu/cpu_platform.c`：CPUID model、1A、1F/0B、6/HFI、x2APIC、TSC、xstate capability 与 MCA inventory。
- `c/kernel/cpu/cpufeat.c`：CPUID feature bits 与 0D/XSAVE geometry inventory；OSXSAVE 为 0 时不执行 XGETBV。
- `c/kernel/cpu/acpi.c`、`smp.c`、`smp_topology.c`：MADT、AP 启动、逐 CPU 采样与实际汇总。
- `c/crypto/cpu_report.c`：启动期诊断，必须区分 `cpuid-addressable` 与实际 online count，并正确显示 1F source、hybrid/unknown 状态。
- `c/kernel/core/ktime.c`：invariant TSC policy、校准与跨 CPU monotonic 保证。

冻结前应再检查四点：

1. 1F parser 对未知上层 domain 按 Intel 算法扩展 package/core mask，接受相等 shift、拒绝 shift 下降，并且不把 EBX 当实际 LP/core 枚举。
2. `cpu_report` 不再把 leaf 1F 显示成 legacy，不显示伪造的 hybrid `cores/package`。
3. 实际 SMP join 保存每个 LP 自己的 1A/1F 结果，不只是 host fixture 有这个接口。
4. HFI/Thread Director 只读 CPUID inventory 不得被描述为启用；微码 revision、安全缓解枚举与策略明确标为未实施，而不是从型号或 BIOS 假设推断已支持。
