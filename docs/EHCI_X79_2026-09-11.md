# EHCI USB 2.0 backend for X79 / C600

The new `c/drivers/usb/ehci.c` binds PCI class `0c:03:20` through the device
model. It registers with the common `usb_hc` layer; hub enumeration, HID
decoding and Bulk-Only mass storage remain separate USB class drivers.

Intel's X79/C600 has two EHCI controllers and two integrated rate matching
hubs, one hub per controller. Each hub has a single transaction translator
(TT). Therefore a high-speed-root-only HCD would not cover a low/full-speed
keyboard behind the chipset's hub. This backend encodes the nearest HS hub's
address and downstream TT port, translates USB speed into EHCI EPS, sets the
control-endpoint flag for asynchronous FS/LS control, and uses start/complete
split masks for periodic interrupt IN. The core preserves the nearest HS TT
when a device is behind an additional full-speed hub.

References:

- [Intel C600 / X79 datasheet, sections 5.20 and 5.21](https://www.intel.com/content/dam/www/public/us/en/documents/datasheets/c600-series-chipset-datasheet.pdf)
- [Intel EHCI 1.0 specification, sections 2, 3.5–3.6, 4.8, 4.12 and 5.1](https://www.intel.com/content/dam/www/public/us/en/documents/technical-specifications/ehci-specification-for-usb.pdf)
- [QEMU USB device documentation](https://www.qemu.org/docs/master/system/devices/usb.html)

## Production behavior

- Up to four independent EHCI controllers, sharing the core's bounded table
  of 32 USB devices. Endpoint state and USB addresses belong to each host.
- Before any BAR access, PCI Command is moved to a readback-confirmed state
  with MEM decode on, INTx suppressed and Bus Master off. EECP is treated as
  a PCI configuration byte offset. The backend requests OS ownership, waits
  up to one second for BIOS release, then clears defined legacy SMI enables.
  A stuck firmware semaphore fails initialization; ownership is not forced.
  Bus Master can be enabled only after an acknowledged controller halt/reset
  and publication of the driver's own schedules, and that enable is itself
  read back. This prevents firmware-owned QH/qTD addresses from resuming DMA.
- qTDs, QHs, the periodic frame list and transfer arenas use the DMA ledger
  with `DMA_MASK_32`. CPU pointers can be in the high kernel physmap. Hardware
  fields contain the independent device address, never a CPU-pointer cast.
- Asynchronous control and bulk use one serialized queue per controller.
  SETUP, data and status carry their proper toggles. A short control-IN qTD
  branches to the status stage, and bulk IN returns its exact completed byte
  count, including a successful zero-length short packet. Transfers up to
  32 KiB use multiple qTDs when needed. Bulk preserves the hardware toggle;
  successful common `CLEAR_FEATURE(ENDPOINT_HALT)` resets backend DATA0.
- The asynchronous schedule must acknowledge `ASS=0` before its queue or
  bounce arena is reused. On an aborted split, the common TT-buffer clear is
  issued from thread context after that stop, not from the interrupt handler.
- Periodic interrupt IN reserves complete frames conservatively. FS/LS uses
  start-split microframe 0 and complete-split opportunities 2–4; HS supports
  subframe polling masks. A request for more bandwidth or unsupported packet
  geometry is refused. IRQ rearming requests `PSE=0`; a later event/timer
  observation of `PSS=0` safely rebuilds the overlay and restarts it. IRQ code
  neither allocates nor waits for that hardware transition. A timer ensures a
  NAK-only keyboard does not strand this handshake without another USB IRQ.
- Transfer and reset waits use the calibrated monotonic clock, with an
  additional bounded iteration ceiling. A timeout is failure, not successful
  completion of a guessed delay.
- Controller teardown closes common admission and drains users, cancels the
  timer, and releases DMA allocations only after `HCHalted` plus a confirmed
  PCI Bus Master clear. A failed stop or config readback quarantines the
  ledger. Static controller identities remain reserved after
  removal so a timer callback already claimed on another CPU cannot target a
  recycled controller. Endpoint DMA arenas are retained until controller
  shutdown rather than individually freed during an uncertain hardware stop.

## Executed verification

`tests/ehci.mk` is included by the root Makefile. Its positive host gate
depends on its negative controls. `make test-mk-wired` passed with 296 fragments
(295 reachable and one declared standalone wrapper).

|---|---|---|
| Whole production `ehci.c` with register/DMA leaves replaced by a host apparatus, ASan/UBSan | 56 checks, zero failures: descriptor geometry, DMA32 boundaries, TT routing, short control/bulk, toggles, nonblocking periodic rearm, BIOS handoff, partial-handoff retention, PCI Command ownership and halt/BME ownership | `build-x79-root-driver-freeze/ehci-host/positive.log` |
| Eleven production fault controls | Each compiled, ran and failed its named assertion: `NO_TT`, `FULL_SHORT`, `IGNORE_BIOS`, `NO_HALT`, `PRE_HANDOFF_BME`, `COMMAND_NO_READBACK`, `MASTER_BEFORE_HALT`, `RESTORE_NO_READBACK`, `CLEAR_MASTER_NO_READBACK`, `POST_HANDOFF_RESTORE_BME`, `SKIP_ISOLATE_ON_HALT_FAIL`; the two new controls each produce exactly one named failure | `build-x79-root-driver-freeze/ehci-host/*.log` |
| One EHCI, QEMU HS keyboard + HS mouse, no i8042 | Key repeat, motion, axis direction, left/right buttons and both wheel signs reached a ring-3 application; EHCI vector had real deliveries and no other registered owner | `build-x79-ehci/release-hid/{serial.log,command.json,result.json}` |

The final ordinary-ISO HID runs record and recheck SHA-256:
`43fb5d839a85cddd2fdf82255c908658572f090d9e2cb4f7fa2fcde89dd5b17b`.
The runner reuses all application assertions in `tests/qmp/qmp_usb.py`; it
changes the QEMU controller fixture and checks EHCI-specific speed/IRQ evidence.
The earlier dual-HC fixture allowed a default NIC to share a vector; the
`dual-exclusive` run removes that ambiguity and is the final evidence.

In the 16 GiB storage run, the caller buffers were at physical addresses
`0x101404025` and `0x10141607b`, both above 4 GiB. EHCI's actual qTD staging
address was `0x40001040`, below 4 GiB. xHCI had its own separate high DMA
buffers. This proves high-memory callers work through EHCI's DMA32 staging;
it does not claim that EHCI itself performed DMA above 4 GiB.

## Deliberate limits

These are QEMU and host-apparatus results, not a physical X79 boot record.
The installed QEMU models real HS HID devices and EHCI USB storage, but its
`usb-hub` model supplies only a full-speed hub. Consequently, TT descriptors
and routing/error-recovery logic have production host coverage; actual split
transactions through an X79 rate matching hub still need physical-board
verification. A UHCI companion run is not substituted for that evidence.

No UHCI/OHCI companion driver, isochronous transfers, high-bandwidth interrupt
endpoints, suspend/resume, dynamic hotplug/rebinding or general periodic
bandwidth scheduler is claimed. Full-speed/low-speed devices attached directly
to an EHCI root port are refused when a companion would be necessary. Complete
frame reservation can reject a device combination that a more sophisticated
TT scheduler could support. Endpoint reservations and DMA remain controller
owned until shutdown, including endpoints whose class later declines to bind.
Actual hardware-stop failure retention is tested by the host fault apparatus;
this document does not claim a physical controller failed-stop experiment.
The legacy `USBLEGCTLSTS` SMI-disable write is not yet read back; a firmware that
ignores that write may leave legacy SMI behavior active even though DMA ownership
and Bus Master transitions remain independently checked.

make BUILD=build-x79-ehci test-ehci-host
make BUILD=build-x79-ehci test-ehci-hid test-ehci-multi
make BUILD=build-x79-storage USB_STORAGE_RAM=16G USB_STORAGE_CPU=SandyBridge test-usb-storage-ehci
