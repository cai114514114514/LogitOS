# X79 + Xeon E5 v1/v2 + 16 GiB DDR3 + GTX 1050 驱动扩展交付（2026-09-11）

## 结果

这一轮已经把目标机器需要的 CPU、内存盘点、启动显示、PCI/中断安全前置条件、
X79/C600 USB、板载 HDA、AHCI/NVMe 存储与常见网卡路径接入或加固生产内核，

## CPU 范围：这里的“E5 全做”指什么

目标是使用 **LGA2011-0** 的 Sandy Bridge-EP 和 Ivy Bridge-EP，也就是 X79
主板上可能实际安装的 Xeon E5 v1/v2 路径，重点覆盖 E5-1600 与 E5-2600
v1/v2。诊断标签识别 Intel family 6/model `0x2d` 和 `0x3e`，真正的功能选择
仍依据 CPUID/MSR 能力，而不是处理器名称字符串。

范围不包含 LGA1356 的 E5-1400/2400，也不包含 LGA2011-3 的 E5 v3/v4。
双路 E5-2600 的 NUMA/QPI、CPU 热插拔和逐 SKU 功耗/睿频行为也没有纳入本次
验收。

这里不能把 Intel X79 的官方兼容页说成 Xeon 官方支持证明。该页面列出的是
Core i7 产品，没有列出 Xeon E5。实际 X79 主板能否点亮某颗 E5，仍取决于
主板 BIOS 与微码；LogitOS 只能在固件已经初始化 CPU 后按能力启动它，不能
修复在进内核前就拒绝处理器的固件。

依据：

- [Intel X79 Express Chipset compatible products](https://www.intel.com/content/www/us/en/products/sku/64015/intel-x79-express-chipset/compatible.html)
- [Intel Xeon E5 v1 datasheet](https://www.intel.com/content/dam/www/public/us/en/documents/datasheets/xeon-e5-1600-2600-vol-1-datasheet.pdf)
- [Intel Xeon E5 v2 datasheet](https://www.intel.com/content/dam/www/public/us/en/documents/datasheets/xeon-e5-v2-datasheet-vol-1.pdf)

## 已进入生产内核的行为

### Xeon E5 v1/v2 与 16 GiB 启动路径

- `PERCPU_MAXCPU` 及关联的 syscall 记账、内核 profiling、堆 magazine 均扩展
  为 32 槽。这覆盖单颗 12 核 24 线程 Ivy Bridge-EP，并消除了原先 CPU 7
  之后静默截断的路径。
- 早期 CPU 盘点解析 CPUID leaf 0B 拓扑、leaf 4 确定性 cache、APIC 模式、
  MCA bank 数量和 invariant TSC。leaf 0B 缺失或畸形时走经过检查的 leaf 1
  加 leaf 4 回退；cache 容量乘法有溢出拒绝。
- `SYS_CPU_COUNT` 使用 ABI 号 196，mini-libc 的 `_SC_NPROCESSORS_ONLN` 返回
  `smp_cpu_count()` 的运行时结果。它没有改变零参数 `SYS_CPU_INDEX` 的约定。
- 当前中断与上下文切换仍使用 FXSAVE/FXRSTOR。BSP 和 AP 启动路径主动清除
  CR4.OSXSAVE；日志把硬件 AVX 与 OS 可用 AVX 分开。迁移到 XSAVE ABI 前，
  内核不会宣称 AVX 可安全使用。
- 16 GiB 客体运行证明内核、SMP 与高内存调用者路径能够在该内存规模下执行；
  它不证明实体主板完成 DDR3 training，也不证明固件发布的可用内存恰好等于
  DIMM 标称容量。

稳定诊断包括：

```text
[cpu-platform] family=6 model=0x2d ... generation=sandy-bridge-ep ...
[cpu-platform] family=6 model=0x3e ... generation=ivy-bridge-ep ...
[smp] 16/16 CPUs online
[smp] 24/24 CPUs online
```

### BIOS/UEFI 的 32 MiB 安全装载

BIOS/GRUB 与自建 UEFI loader 现在使用同一个 ELF `p_paddr`：内核从 32 MiB
开始，仍完整位于 `boot.asm` 建立的首个 1 GiB 恒等映射。链接器同时导出
`_kernel_start`/`_kernel_end`，panic/backtrace 的内核地址判断不再复制一个
容易漂移的 1 MiB 常量。最终 ELF 的 Multiboot2 header 位于文件偏移 344，
保持 8-byte 对齐并落在 GRUB 要求的前 32 KiB。

UEFI loader 只接受 `AllocatePages(AllocateAddress, EfiLoaderData)` 对整个
PT_LOAD page span 的直接分配。它在分配后读取内存图一次，并在每个
`ExitBootServices` 尝试使用的最终 map/key 上再次确认目标区间无洞、无溢出，
且所有相交 descriptor 都是 LoaderData。任何 ACPI NVS、ACPI reclaim、
BootServices、Conventional、Reserved 或未描述字节都会在 EBS 前明确拒绝。
trampoline 不再接受 source/destination/length，也没有 EBS 后 kernel copy。

CPU 模式下降还在 long mode 且 `CR0.PG=1` 时先清除 `CR4.PCIDE`，并用新鲜
读回确认 bit 17 已清，随后才进入 32-bit compatibility code 并清 `CR0.PG`。
这是 Intel 对分页模式转换的硬约束；跳过、取消读回或延后清除都会在专门的
生产汇编变异门中失败。X79 支持的 E5 v1/v2 没有五级分页；面向更新平台时仍
需要在重新采用这条 loader 前为 `CR4.LA57` 建立同等级别的状态合同。
寄存器转换依据 [Intel 64 and IA-32 SDM](https://cdrdv2-public.intel.com/922486/325384-092-sdm-vol-3abcd.pdf)。

这仍是固定地址、不可重定位的内核；若某台实体固件确实占用 32 MiB 起的完整
image span，安全结果是拒绝启动并打印冲突，而不是覆盖固件。本轮 QEMU OVMF
通过不能证明用户的 X79 固件一定提供该区间。

### X79/C600 SMBus 与 DDR3 SPD

- 驱动只接受 Intel `8086:1d22` 且 PCI 类为 `0c:05` 的 D31:F3 SMBus
  控制器，不用类号泛绑未知寄存器布局。
- 使用 BAR4 的 32-byte I/O 窗口。设置 PCI I/O decode 后立即读回 Command；
  写入未生效时，在第一次端口访问前恢复并拒绝绑定。`HOSTC.HST_EN` 同样读回
  确认；若 HST_EN 失败后的旧 Command 恢复也无法读回确认，本次启动永久隔离
  该控制器，后续重探测在任何 BAR 端口访问前拒绝。`HOSTC.I2C_EN` 模式直接
  拒绝。
- 只向 `0x50..0x57` 发 SMBus Byte Data read。没有任意地址接口，没有 SPD
  写命令。总线锁、空闲、传输与 KILL 都有真实时间和轮询上限，且只 KILL
  本驱动已经发起的超时事务。KILL 后必须读回 `HOST_BUSY=0`；若硬件忽略
  KILL，则保留 KILL 和 INUSE ownership 并永久隔离控制器，避免后来者与仍在
  运行的事务相撞。
- DDR3 解码读取 byte 0..145，按 byte 0 bit 7 选择 117-byte 或 126-byte
  CRC 覆盖范围，并计算 density、device width、primary bus width 与 ranks。
  ECC extension、厂商原始字节、序列号和清理后的 part number 分开报告。

```text
[smbus] 0000:00:1f.3 Intel C600/X79 io=0x... SPD read-only 0x50-0x57
[spd] addr=0x50 ddr3 module_mib=16384 ... crc=ok ...
[spd] modules=1 module_capacity_mib=16384 ... source=SPD-not-firmware-map
```

`module_capacity_mib` 是 SPD 描述的模块容量，不是固件内存图中的可用 RAM。
固件保留区、training 结果、memory remap 与坏内存都可能使两者不同。

### GTX 1050：固件启动帧缓冲保持

生产探针只认 NVIDIA `10de` 下列设备 ID：

| 产品 | Device ID |
|---|---|
| GeForce GTX 1050 | `1c22`, `1c62`, `1c81`, `1c83`, `1c8d`, `1c91`, `1c92` |
| GeForce GTX 1050 Ti | `1c21`, `1c61`, `1c82`, `1c8c`, `1c8f` |

相邻 Pascal ID 不作为别名；例如 `1c90` 是 MX150，`1cb3` 是 Quadro P400。
探针要求 type-0 PCI 显示控制器、已开启的 MEM decode、D0 电源状态、有效内存
BAR，以及完整落在该函数 BAR 内的 Multiboot2/UEFI GOP 线性帧缓冲。任何条件
不满足都拒绝绑定，不尝试唤醒或重置显卡。

成功边界是保持固件已经扫描输出的桌面，并发布：

```text
[nv-bootfb] ... 10de:1c81 GeForce GTX 1050 mode=passive ... pm=D0 ...
[nv-bootfb] framebuffer retained; no GPU MMIO, modeset, clocks, DMA, IRQ or 3D
```

这不是 Pascal 原生显卡驱动。本轮没有 GP107 固件上传、显存控制器初始化、
display-head modeset、reclock、命令通道、显存分配、2D/3D 加速、CUDA、
多显示器、休眠恢复或 HDMI 音频。实体首启成功的含义也仅是桌面持续可见且
帧缓冲归属得到确认。

设备 ID 依据：[NVIDIA supported products](https://download.nvidia.com/XFree86/Linux-x86_64/595.45.04/README/supportedchips.html)。

### PCI BAR 安全前置条件

GTX 1050 探针本身不写 PCI 配置或 GPU MMIO，但通用 PCI 枚举器必须通过
“写全 1”测量 BAR。因此枚举器现在串行化完整测量事务，先关闭 I/O/MEM
decode 并读回确认，再测量 32-bit、64-bit 与 I/O BAR；随后逐个恢复 BAR
低/高半部和原始 Command，并对每一步做读回检查。

如果 decode 无法关闭、只关闭了一部分、BAR 任一半无法恢复，或 Command
无法恢复，枚举器不会发布该 resource；恢复不确定时保持 decode 关闭。这一
前置条件避免“被动显卡驱动”接收到显卡仍在响应时测得的伪 BAR。

### 通用 PCI Command 与 DMA 接管

通用设备层新增了有返回值的 PCI Command 写后读回合同。它只依据枚举到的 BAR
类型开启 I/O 或 MEM decode，避免纯 MMIO 实体设备因硬连为零的 I/O enable 位
被误拒绝；`bus_master=false` 会明确清除 BME。启用失败时在任何 BAR/私有 DMA
地址访问前尝试恢复原 Command，停用失败时不会为了“恢复”而重新打开 decode
或 BME。配置空间读回只证明 PCI 门控位，控制器停止仍由各驱动单独确认。

NVMe、QEMU EDU、e1000/e1000e、PCnet、RTL8139/RTL8168/8169 与 virtio 公共
路径已经迁移到这一合同。NVMe 先在 BME 关闭时确认 `CC.EN=0/CSTS.RDY=0`，发布
admin queue 后才开启 BME，再设置 `CC.EN=1`；后续初始化失败统一走控制器停止、
DMA 回收和 PCI disable。82574 在把 PMCSR 从 D3 切回 D0 前先清 BME，避免固件
旧 ring 在 10 ms 唤醒窗口恢复 DMA。AHCI、HDA、EHCI 与 xHCI 保留更严格的
设备专用等价状态机。

### X79/C600 EHCI USB 2.0

- HCD 通过 PCI 类 `0c:03:20` 接入通用 USB host-controller 层，支持最多四个
  独立 EHCI 控制器。
- BAR 访问前先把 PCI Command 移到经读回确认的 MEM-on、Bus-Master-off、
  INTx-disabled 状态；完成 BIOS ownership、控制器 halt/reset 和本驱动队列
  发布后才启用并读回确认 Bus Master，避免恢复固件留下的旧 qTD/QH DMA。
- BIOS ownership handoff 有一秒上限；固件不释放时初始化失败，不强抢。
- qTD、QH、periodic frame list 和传输 arena 通过 DMA ledger 分配并限制为
  DMA32。高于 4 GiB 的调用者缓冲区通过低地址 staging 传输。
- 异步 control/bulk 保留正确 toggle、短包与实际完成长度；周期 interrupt IN
  支持 HS，并为 FS/LS 设备编码最近的 HS hub、TT port 与 split mask。
- 控制器停止不确定时隔离 DMA ledger，不把可能仍被硬件使用的内存重新分配。

未覆盖 UHCI/OHCI companion、isochronous、高带宽 interrupt、通用带宽调度、
动态热插拔和 suspend/resume。QEMU 的 EHCI 事务也没有替代实体 X79 rate
matching hub 上真实 split transaction 的验证。

### PCIe xHCI USB 3 扩展控制器

- 驱动按标准 PCI 类 `0c:03:30` 匹配，不依赖某个 QEMU 或厂商 device ID；这能
  接住许多 X79 主板上额外焊接或插卡提供的 USB 3 控制器，但不代表每种 ASMedia、
  Renesas 或 VIA 固件怪癖已经在实体机验证。
- BAR 访问前先把 PCI Command 移到经读回确认的 MEM-on、BME-off、
  INTx-disabled 状态。xHCI legacy capability 链若畸形、循环或 BIOS semaphore
  一秒内不释放，驱动保持 BME 关闭并拒绝控制器，不会强制清 SMI 后继续。
- handoff、`RS=0/HCH=1/CRCR.CRR=0`、controller reset 和自有 DCBAA/command/
  event rings 都确认完成后才启用并读回 BME。USB host-controller table 已满等
  late probe failure 也必须执行同一 stop/isolate 证明。
- shutdown 或失败恢复无法同时确认控制器停止与 BME 清零时，DMA ledger 和
  controller identity 一起保留并隔离；同一设备不会重探，也不会释放可能仍被
  硬件引用的 ring。

X79/C600 原生 USB 2 路径仍是上一节的 EHCI。此节覆盖常见的附加 xHCI 路径，
不声称已经拿到用户主板上那颗实际 USB 3 芯片的 vendor/device ID。

当前实现由单个静态 xHCI 实例承载，只有枚举到的第一颗 `0c:03:30` 控制器能够
注册；第二颗 xHCI 会被拒绝。设备与 hub 只在启动探测阶段枚举一次，没有运行时
热插拔线程。实体首启应把键盘、鼠标和需要测试的 U 盘预先接到 X79 EHCI 或第一
颗 xHCI 上；若接在第二颗附加控制器或启动后才插入，本轮内核不会发现它。

### X79/C600 板载 HDA

- 如果完整 PCI 拓扑中存在 `0000:00:1b.0 8086:1d20`，HDA 单实例优先绑定它；
  其他独立 HDA 控制器只在没有该函数时作为回退。和 PCI 显示函数同一槽位的
  音频函数会在启用设备或映射 BAR 前跳过，避免 GTX 1050 的 HDMI/DP HDA 抢占
  板载模拟音频。
- PCI Command 先进入经读回确认的 MEM-on、BME-off 静默状态。驱动依据 GCAP
  遍历 CORB、RIRB 以及所有 input/output/bidirectional stream，逐项清除并确认
  RUN；只有固件留下的所有 DMA 引擎确实停止后，才执行 CRST 低/高复位。
- `CORBSIZE` 使用规范偏移 `0x4e`；CORB/RIRB 读取 capability bits、选择控制器
  真正支持的 2、16 或 256 entry 深度并验证写回。自有 ring 分配、提交和基址
  写入完成后才启用并读回 BME，然后再启 ring；codec 指针按实际深度回卷。
- 控制器复位必须观察 CRST 两个方向的读回；失败探测会停 CORB、RIRB、流引擎
  与总控。无法确认停机时保留并隔离硬件仍可能访问的 DMA 对象，同时允许后续
  板载控制器继续探测。
- 播放与采集共享一个设备 IRQ。IRQ 只在全部可能失败的注册完成后发布；解绑时
  必须先确认设备中断源释放，失败则保留回调、DMA 和可重试实例。处于 removing
  状态的 ISR 仍读取 `INTSTS` 并 W1C 清除两个流的实际 BCIS/FIFOE/DESE，只抑制
  上层 period callback，防止共享电平中断持续拉住线路。

具体 codec widget 图、机箱前面板引脚、自动静音、插孔检测、HDMI 音频与实体
板载 codec 的电气行为仍需真机日志和听录音验收；精确控制器选择本身不证明某个
OEM codec 拓扑可用。

### X79 SATA AHCI

- AHCI 只匹配 PCI class/subclass/prog-if `01:06:01`。RAID 或 IDE 模式不会被
  当成 AHCI；实体机固件应把 X79 SATA 控制器设为 AHCI。
- BAR5 映射前只启用并读回确认 MEM decode，Bus Master 保持固件原状态；任一
  写入未生效时先恢复旧 Command、再次读回，再拒绝触碰 ABAR。若部分 enable
  已生效而旧 Command 也无法恢复，内核立即 fail-stop；它不会在 Bus Master
  ownership 未知时继续枚举并把潜在后台 DMA 当成普通的“驱动没找到”。
- 若控制器声明 BIOS/OS handoff，驱动请求 OS ownership 并等待 BIOS busy 与
  owned 位释放。固件不释放时拒绝初始化，不强抢端口。handoff 完成后，若固件
  原先留下 BME，驱动先关闭并读回；随后逐个 PI 端口确认 `ST/CR/FRE/FR` 全部
  清零，最后才重新启用并确认 BME。恢复或隔离结果不确定时直接 fail-stop；可
  安全隔离的故障会永久记住该 BDF，重探不会再次访问 config 或 BAR。
- 当前块层以 512-byte logical sector 为合同。512e 的物理 4 KiB 分组可以使用；
  native 4Kn 和无效的零逻辑扇区会在注册磁盘前拒绝。QEMU 没有提供本轮可用的
  native 4Kn AHCI 模型，所以 4Kn 结论来自生产 IDENTIFY 解码夹具，不是客体盘。

C600 系列某些主板还会把端口接到 SCU/SAS/RSTe/RAID 控制器。本轮没有实现
Intel `isci`、SCU、SAS 或 RSTe RAID 路径；这些端口即使固件能看到硬盘，也不能
作为 LogitOS 根盘。未知型号实体机应先把系统盘接到 PCH SATA 口并在固件中选择
AHCI，确认 PCI 类为 `01:06:01`。

### Intel 82579LM/V 板载网卡

`e1000-pch2` 与已有 82574 路径分离，只接受 Intel `8086:1502`（82579LM）和
`8086:1503`（82579V）Ethernet function。它在 D3→D0 前关闭 Bus Master，要求
128 KiB BAR0、有效的自动装载 NVM、82579 PHY ID、有效非零单播 RAR0，并通过
PCH2 SWFLAG/HV MDIO 规则完成 PHY 初始化。收发采用 DMA32 coherent legacy
descriptor，TX 只在 DD 后计完成，RX 拒绝缺 EOP、错误与越界帧。

本轮没有实现 ME/AMT 管理固件协作、软件 NVM/LCD 配置、flash 修复、EEE/K1、
WoL、休眠恢复或 MSI。`FWSM.FW_VALID=1` 会打印
`managed-firmware path not implemented` 并拒绝复位 PHY；LM/V 后缀本身不能
保证走非管理路径。复位完成未确认时只从 PCI config 隔离，不再读写 CTRL；IRQ、
master drain 或 SWFLAG 释放无法确认时保留并隔离 DMA，避免重用仍可能被硬件
访问的内存。

平台关系依据 [Intel C600/X79 datasheet §5.4](https://www.intel.com/content/dam/www/public/us/en/documents/datasheets/c600-series-chipset-datasheet.pdf)；
初始化行为还与 Linux 主线 [e1000e/ich8lan.c](https://github.com/torvalds/linux/blob/master/drivers/net/ethernet/intel/e1000e/ich8lan.c)
交叉核对。QEMU 的 `e1000e` 是 82574L，不能作为 82579 证据。

未知 X79 改板也可能使用已有的 Intel 82574 路径（`8086:10d3/10f6`）或
Realtek RTL8168/8111 路径（`10ec:8168/8161`）。其中 RTL 路径尚未在实体网卡
运行；常见的 Atheros、Broadcom 或 Marvell 型号若不在精确匹配表中会保持未
绑定。网络不是本轮根文件系统挂载的前提，首启应先记录完整 PCI ID，再决定是否
需要补充对应驱动。

## x2APIC、SMP 与设备中断

- MADT 同时解析 type 0 Local APIC 与 type 9 Local x2APIC。type 9 的 APIC ID
  和 ACPI UID 保留全部 32 位；ID+UID 完全重复的记录去重，只复用其中一个字段
  的冲突记录拒绝。只启动 flags bit 0 `Enabled` 的 CPU；仅有 `Online Capable`
  的记录留给尚未实现的 ACPI CPU hotplug。
- 普通镜像保持各 CPU 的 `IA32_APIC_BASE` 固件模式。xAPIC 继续使用 MMIO；
  x2APIC 使用 APIC MSR，64 位 ICR 保留 32 位目的 ID。普通镜像不会自行切换
  xAPIC→x2APIC；合成客体的 `LOGIT_X2APIC_QEMU_TEST` 会明确打印
  `TEST-ONLY-force`。
- INIT 到首个 SIPI 至少 10 ms，两个 SIPI 间至少 200 us，使用已初始化的单调
  时钟；时钟停滞、ICR 发送失败或 AP 超时均拒绝继续。每个 AP 使用固定 slot
  与 mailbox；发出启动 IPI 后，失败或迟到 AP 的栈会隔离，避免释放后被迟到
  AP 使用。
- IOAPIC 路由先 mask、写完整 RTE、读回，再解 mask 并读回。因为尚无 VT-d
  interrupt remapping/EIM，IOAPIC、MSI 与 MSI-X 只接受可由 legacy 8 位物理
  destination 表达的 `0x00..0xfe`，不会截断更宽 x2APIC ID。
- PCI INTx、MSI 与 MSI-X 在分配向量、回退或解绑前都先停源并读回。停源失败
  时保留 mode、vector、handler、共享成员与驱动实例；`dev_unbind()` 取消解绑，
  不会在仍可能触发 IRQ 时调用 remove。PIC fallback 下 AP 的本地 timer 中断仍
  向本地 LAPIC 发送 EOI。

合成 BIOS/UEFI 客体证明生产内核的 type 9、MSR backend、完整目的 ID 与 AP
启动能协同工作；它使用测试专用强制开关和 QEMU 稀疏拓扑。实体 X79 的固件
handoff、全部 AP、定时器与设备中断仍为未验证。

## 实体安装介质与固件前提

- GTX 1050 必须由 BIOS/GRUB VBE 或 UEFI GOP 先建立 Multiboot2 type 8、32-bpp
  direct-RGB 线性帧缓冲；没有该 tag 时 `fb_init()` 会停止启动。本轮 GPU 探针
  只验证并保留这段 LFB，不会通过 Pascal 寄存器自行设定显示模式。
- 实体根文件系统必须在早期 block 初始化能够发现的 NVMe、AHCI SATA 或 legacy
  ATA 介质上。X79 SATA 应在固件中设为 AHCI，使控制器报告 PCI 类
  `01:06:01`；RAID/厂商模式不会被 AHCI 驱动误绑。当前块 ABI 要求 512-byte
  logical sector，512e 可用，native 4Kn 会明确拒绝。
- C602/C606 等 C600 改板若把磁盘接在 SCU/SAS/RSTe/RAID 端口，当前内核不会
  发现它。实体首启必须把根盘接到 PCH AHCI SATA 口，并从 PCI 枚举日志确认它
  报告 `01:06:01`；固件界面里能看到磁盘本身不构成可启动证据。
- USB HCD 与 USB mass-storage 在 `dev_probe_all()` 才启动，而根设备选择和
  `vfs_mount()` 在它之前。因此当前普通启动不能从同一 USB mass-storage 获得
  LogitFS 根盘。`logit.iso`/`esp.img` 是启动介质，`disk.img` 必须放在另一个
  能早期发现的实体盘或分区；本轮不会自动覆盖用户磁盘。
- USB 设备应在上电前插好。xHCI 只接管第一颗控制器并只做启动期枚举；启动后
  热插拔、第二颗附加 xHCI 及其端口当前不可用。优先把键鼠接到 X79/C600 的
  EHCI USB 2.0 口，或确认接在第一颗 xHCI 上。
- PCI INTx 回退当前使用固件写入 configuration byte `0x3c` 的 IRQ Line，再套用
  MADT ISA override。内核尚无 AML `_PRT` 求值和 PCI bridge INTx swizzle；设备
  不能用 MSI/MSI-X、且固件未正确填写 IRQ Line 时会保持轮询或拒绝中断绑定。
  PCI 配置域目前也只支持 segment 0，ACPI 只采用首个 IOAPIC。
- 早期串口日志固定使用 legacy `COM1` I/O `0x3f8`、38400 baud、8N1。内核不
  解析 ACPI SPCR，也不自动发现 PCI/USB 串口；主板需要 16550-compatible COM1
  和正确电平转换。没有串口输出时仍应观察显示器并在桌面出现后导出 klog，不能
  只凭“串口安静”判断内核没有启动。
- PS/2 初始化路径会启用控制器与 IRQ，但当前命令等待没有验证设备存在或 ACK
  值。`mouse + keyboard armed` 只表示事件处理路径已启用；必须收到真实按键和
  鼠标事件，才算该主板的 PS/2 输入通过。

## 实体 X79 首启验收

首次启动应在主板具备 legacy COM1 时按 `0x3f8, 38400 8N1` 保存完整串口日志，
并始终同时观察显示器；没有兼容串口时从桌面导出 klog。建议按下面顺序判断：

1. 固件已经识别 Xeon，LogitOS 输出 `[cpu-platform]`、`[lapic]` 和 `[smp]`；
   online 数量与处理器线程数一致。固件在进入内核前拒绝 CPU 时不属于 OS
   驱动可以修复的范围。
2. `[dev] 0000:00:1f.3 8086:1d22 class=0c.05` 绑定 `c600-smbus`，随后
   `[spd]` 的 `crc=ok` 模块容量合计为预期 16384 MiB。
3. 将 SPD 的 `module_capacity_mib` 与固件内存图/系统 usable RAM 分开记录；
   容量缺口不能直接归因于 SPD 驱动。
4. GTX 1050 是固件 primary display，出现 `driver=nv-bootfb` 与 no-takeover
   诊断；绑定前后桌面持续可见，LFB 完整落在该 PCI function 的 BAR 内。
5. 启动前把键鼠接到 X79/C600 EHCI 端口；控制器、集成 hub、键盘鼠标分别留下
   枚举和真实输入事件。若低/全速设备依赖 rate matching hub，记录实际 TT/split
   结果；只出现 `armed` 不算设备通过。
6. 若主板另有 `class=0c.03 prog-if=30` 的 USB 3 控制器，记录其 vendor/device、
   BIOS handoff、BME 时序及预插 USB 2/3 设备传输；当前只验收第一颗 xHCI，第二
   颗与启动后热插拔不在通过范围。没有该类设备不是 X79 EHCI 失败。
7. X79 SATA 控制器以 `class=01.06 prog-if=01` 出现并注册 `ahci0`；实际系统盘
   完成读取、写入、flush、关机和冷启动读回。出现 4Kn 拒绝时不要改写扇区大小；
   SCU/SAS/RSTe/RAID 端口不能作为本轮根盘。
8. 若板载网卡是 `8086:1502/1503`，记录它绑定 `e1000-pch2` 或具体 refusal；
   若是 82574 或 RTL8168/8111，则记录其精确 ID 与对应绑定。只有出现 link up、
   DHCP、收发与冷启动结果后才算该主板网络通过。
9. `00:1b.0 8086:1d20` 应优先绑定板载 HDA；扬声器/耳机播放和麦克风采集要分别
   实听/回放，日志选择正确控制器不能替代 codec 电气验收。
10. 保留所有 refusal、timeout、CRC error 和未绑定行。它们用于定位具体主板
   差异，不应通过扩大设备 ID 或跳过读回检查来隐藏。

只有完成这组普通镜像实体启动，才能把相应项目从“未验证”改为“实体通过”。
即使 GTX 1050 首启画面成功，也仍然只能声称 firmware boot framebuffer
保持，不能声称原生 modeset 或 3D 加速。

宿主门：

```sh
make BUILD=build-x79-review test-driver-host
make BUILD=build-x79-review test-xeon-e5-host
make BUILD=build-x79-review test-x79-chipset-host
make BUILD=build-x79-review test-nvidia-pascal-host
make BUILD=build-x79-review test-pci-bar-safety-host
make BUILD=build-x79-review test-ehci-host
make BUILD=build-x79-review test-xhci-lifecycle-host test-xhci-xfer-host test-usb-hub-host
make BUILD=build-x79-review test-storage-hardware-host
make BUILD=build-x79-review test-e1000-pch2-host
make BUILD=build-x79-review test-hda-x79-host
make BUILD=build-x79-review test-uefi-load-policy-host test-uefi-pcide-host
```

现有 QEMU 验收入口：

```sh
make BUILD=build-x79-xeon test-xeon-e5-bios
make BUILD=build-x79-xeon test-xeon-e5-uefi
make BUILD=build-x79-xeon test-xeon-e5-cap-control
make BUILD=build-x79-xeon test-xeon-e5-osxsave-control
make BUILD=build-x79-pascal-synth PASCALVERIFY=1 test-nvidia-pascal-synthetic-guest
make BUILD=build-x79-ehci test-ehci-hid test-ehci-multi
make BUILD=build-x79-storage USB_STORAGE_RAM=16G USB_STORAGE_CPU=SandyBridge test-usb-storage-ehci
make BUILD=build-x79-storage USB_STORAGE_RAM=16G test-usb-storage-dual
make BUILD=build-x79-storage test-ahci-sector
make BUILD=build-x79-storage test-nvme-bridge test-nvme-bridge-uefi
make BUILD=build-x79-x2apic-synth test-x2apic-synthetic-guest
make BUILD=build-x79-uefi-review test-uefi test-uefi-negctl test-uefi-pcide
```

`BUILD=` 必须作为 `make` 的命令行赋值；这些测试需要独立目录。GTX 的
`PASCALVERIFY=1` 只用于 QEMU stdvga 合成验收，不能用于最终实体镜像。
统一的 `test-driver-host` 是宿主驱动矩阵入口；旧 `test-x79-host` 没有覆盖 HDA、
82579 与完整 x2APIC/INTx 门，不能当成本报告的总验收入口。
