# Trust roots and package signing

LogitOS uses Ed25519 signatures for package payloads and application images. Packages (`.lpk`) and applications (`.aex`) share a compiled signer table, with different signed messages and acceptance policies. TLS certificate validation uses a generated CA root store, while AMD Polaris firmware loading checks compiled SHA-256 pins. The signature formats and signer accessors live in `c/crypto/trust/`.

## Trust stores

| Purpose | Source inputs | Generated representation | Consumer |
|---|---|---|---|
| Package and application signatures | Public keys in `tools/pkgroots/` | `c/crypto/trust/pkgroots.inc` | Package verifier and AEX parser |
| TLS certificate chains | Certificate PEMs in `tools/roots/` | `c/crypto/trust/roots_bundle.inc` | X.509 chain verifier |
| AMD Polaris firmware integrity | Digests in `third_party/amd-firmware/MANIFEST` | Header generated by `tools/gpu/amd/fwpin.py` | Polaris firmware resource loader |

Each package signer entry contains a name and a raw 32-byte Ed25519 public key. `pkg_root_count()`, `pkg_root_key()` and `pkg_root_name()` expose the table. Package and application verification call these accessors, which also serve signer listings. In `c/crypto/trust/pkgsig.c`, compiler poisoning prevents direct references to the underlying array below the accessors.

The rationale in `c/crypto/trust/pkgsig.h` ties trust storage to filesystem ownership: protecting keys stored on disk requires enforced ownership that survives reboot. Compiling public keys into each verifier binds its trust decisions to the software image containing it.

The kernel, guest package utility and host tools each embed a copy of the signer table. `Makefile` declares dependencies on `c/crypto/trust/pkgroots.inc` for the kernel and guest verifier objects and the host package tool. `tests/aexsig.mk` declares the corresponding dependency for the host application signer.

## Signed packages

`c/crypto/trust/pkgsig.h` defines a fixed 224-byte header followed by the payload. Integer fields use little-endian encoding.

| Offset | Bytes | Contents |
|---|---:|---|
| 0 | 8 | Magic string `LOGITPKG` |
| 8 | 4 | Format version, currently 1 |
| 12 | 4 | Flags, zero |
| 16 | 8 | Payload length |
| 24 | 4 | Name length, at most 64 bytes |
| 28 | 4 | Reserved field, zero |
| 32 | 64 | Payload name, padded with zero bytes |
| 96 | 32 | SHA-256 digest of the payload |
| 128 | 32 | Signer public key |
| 160 | 64 | Ed25519 signature |
| 224 | Payload length | Payload bytes |

`lpk_sign()` in `c/crypto/trust/pkgsig.c` hashes the payload, fills the header and signs this 32-byte message:

```text
SHA-256("LOGITOS-lpk-v1" || header[0:160])
```

The domain string contributes its bytes before the terminating zero. The signed header binds the name, payload length, payload digest and signer public key. Hashing the manifest gives Ed25519 a fixed message size as the payload grows; the binding to the payload rests on SHA-256 collision resistance.

`lpk_verify()` performs these checks in order:

1. Validate arguments, header size, magic, version, flags, reserved field and lengths.
2. Require zero padding after the name; reject embedded zero bytes, `/`, `\` and bytes below `0x20` within it.
3. Compare the payload’s SHA-256 digest with the header.
4. Verify the Ed25519 signature.
5. Match the signer public key against the compiled root table.

Checking the payload digest first rejects damaged data before curve arithmetic. Comparing the declared payload length against the bytes remaining after the header avoids overflow in a header-plus-length calculation.

Success returns `LPK_OK` and fills a `struct lpk` with the payload view, name, signer and root index. The caller keeps the input buffer alive while using that payload view. The error constants in `c/crypto/trust/pkgsig.h` distinguish truncation, bad magic, unsupported version, malformed fields, digest mismatch, invalid signature and an untrusted signer.

The caller supplies `trust_any`. A nonzero value accepts a valid signature from an unknown key and returns `root_index == -1` for that signer. A known signer retains its matching root index. Because the choice arrives as a caller argument, the caller controls trust acceptance.

## Package tools

`tools/lpk.c` implements the host package tool using the same package and cryptographic sources as the guest verifier. From the repository root, `make build/lpk` builds it with the default build directory.

| Command syntax | Operation |
|---|---|
| `build/lpk sign <seed-hex> <name> <in> <out>` | Sign the input payload and write a package |
| `build/lpk verify <file> [--any]` | Verify a package, optionally accepting an unknown signer |
| `build/lpk roots` | List the tool’s compiled signer keys |
| `build/lpk keygen` | Generate and print an Ed25519 seed and public key |

Signing takes a 32-byte seed encoded as 64 hexadecimal characters. Key generation reads host entropy from `/dev/urandom` and exits with an error if it cannot obtain the requested bytes (`tools/lpk.c`).

The guest utility is implemented in `c/apps/coreutils/pkgverify.c` and installed as `/bin/pkgverify` by `Makefile`.

| Guest command syntax | Operation |
|---|---|
| `pkgverify <file.lpk>` | Verify against compiled signer keys |
| `pkgverify --any <file.lpk>` | Accept a valid signature from an unknown signer |
| `pkgverify --roots` | List the utility’s compiled signer keys |

Verification prints `PKG_OK` or `PKG_REFUSED`. The root listing reads the table embedded in the utility itself, through the package root accessors.

## Application signatures

AEX metadata can carry an `AEX_T_SIG` record, defined in `c/kernel/exec/load/aex.h`. Its value contains a 32-byte signer public key followed by a 64-byte Ed25519 signature. `AEX_SIG_LEN` in `c/crypto/trust/aexsig.h` defines the total as 96 bytes.

`aex_sig_sign()` signs this digest:

```text
SHA-256("LOGITOS-aex-v1" || elf_size_le64 || SHA-256(ELF))
```

The domain string contributes its bytes before the terminating zero, and the ELF size occupies eight little-endian bytes. Package and application signatures use different domain strings and manifest layouts. Both verifiers obtain trusted keys through the package root accessors (`c/crypto/trust/aexsig.c`, `c/crypto/trust/pkgsig.c`).

`tools/aexsign.c` reads an ELF image from standard input and prints its signer public key and signature as hexadecimal fields. `tools/mkaex.py` invokes this tool when given `--sign-seed` and `--aexsign-bin`. It inserts the resulting record before calculating metadata padding, so the padding accounts for the signature’s space. A signer failure terminates container generation.

The parser in `c/kernel/exec/load/aex.c` serves both buffer and path inputs. After validating the metadata and ELF CRC-32, a container carrying a signature record receives an ELF SHA-256 calculation and a call to `aex_sig_verify()`.

| Status | Meaning |
|---|---|
| `AEX_SIG_ABSENT` | Signature record absent |
| `AEX_SIG_INVALID` | Verification failed, or the parser encountered a read failure while hashing the ELF |
| `AEX_SIG_UNTRUSTED` | Signature valid under a key outside the compiled signer table |
| `AEX_SIG_OK` | Signature valid under a compiled signer key |

`aex_sig_verify()` returns the three verdicts for a present record. The parser initializes the absent status and handles hashing failures. It stores the verdict in `struct aex_info`, together with the claimed signer bytes and a root index for `AEX_SIG_OK`.

The parser logs every present signature’s verdict. For unsigned containers reaching this check, it increments a counter and prints the unsigned notice once per boot. Its loading policy is documented under Limitations.

## Development keys and root updates

The generated signer table contains one entry, `logitos-dev`, from `tools/pkgroots/logitos-dev.pub`. Its matching private seed is published in `tools/pkgroots/DEV-SIGNING-KEY.txt`.

The development key lets contributors reproduce and extend signed fixtures. `Makefile` uses it for a trusted package fixture, and `tests/aexsig.mk` uses it for a signed application fixture. Both fixture sets also exercise signatures from a key outside the shipped trust set.

`tools/genpkgroots.py` reads `.pub` files in filename order and derives each signer name from the filename. Each input supplies one line of 64 hexadecimal characters; blank lines and comment lines are permitted. The generator rejects duplicate keys under different names. An empty input set generates a table with zero trusted signers.

After changing the public key inputs, run this command from the repository root to update `c/crypto/trust/pkgroots.inc`:

```sh
python3 tools/genpkgroots.py tools/pkgroots c/crypto/trust/pkgroots.inc
```

Distributing the updated trust set requires rebuilding the kernel, guest verifier and host tools that embed it. The development key files describe replacing the development root with a public key whose private material is kept outside the repository.

## TLS trust anchors

`tools/genroots.py` extracts public keys from certificate PEMs in `tools/roots/` and writes `c/crypto/trust/roots_bundle.inc`. `c/crypto/trust/roots.c` includes the generated table. Its `struct root_ca` entries represent RSA keys, supported EC keys and Ed25519 keys (`c/crypto/trust/roots.h`).

The chain verifier in `c/net/tls/x509.c` anchors a path by matching a certificate’s public key against a stored root key or verifying the path’s top certificate with a stored root key.

The generator records skipped certificates and their reasons in the bundle. Producing a bundle with zero usable anchors requires `--allow-empty`. `trust_banner()` in `c/net/tls/tls.c` reports root names, counts and skip information. The `check-roots` target in `Makefile` regenerates the bundle into the build directory and compares it with the repository copy.

## Firmware digest pins

AMD Polaris firmware pins come from `third_party/amd-firmware/MANIFEST`, which records an upstream revision and file digests. `Makefile` invokes `tools/gpu/amd/fwpin.py` and makes the firmware resource loader object depend on the generated header. Changing the manifest and rebuilding updates the compiled pins.

The loader in `c/drivers/gpu/amd/polaris/resource/files.c` first tries the guest directory `/lib/firmware/amdgpu/`. If that candidate fails, it tries a boot module with the same firmware filename. Disk candidates must be regular files owned by root, with group and other write permissions cleared.

Both sources supply heap buffers that pass format validation and a SHA-256 comparison against the compiled pin for that filename. Missing pins and digest mismatches reject the candidate. Checking the heap buffer binds the verdict to the bytes retained for use.

`tools/mkesp.py` supports firmware delivery through `--firmware-dir`. It places firmware files and an index on the EFI System Partition. `c/boot/efi/loader.c` reads the indexed files and describes them as boot modules for the kernel.

## Verification coverage

These targets define checks for the signing mechanisms. The table describes their source and assertions; the commands were not run for this documentation review.

| Target | Coverage |
|---|---|
| `test-pkg` | Package round trips, malformed fields, corruption, signatures and unknown signers |
| `test-pkg-control` | Requires the package tests to fail with signature checking removed |
| `test-pkg-roots` | Adds a signer to a scratch root table and checks the change from refusal to acceptance |
| `test-pkg-poison` | Compiles the unmodified verifier, then requires a direct root-array reference below the accessors to fail compilation with a poisoning diagnostic |
| `test-pkg-os` | Guest verification, signer listing, unknown signers and extraction reporting |
| `test-aex-sig` | Trusted, tampered, unknown-signer and unsigned AEX cases, plus rejection of a package signature presented as an AEX signature |

`tests/crypto.mk` defines the package verification targets; `Makefile` holds the root-table checks. `tests/aexsig.mk` defines the application fixtures and test target. Its tampered fixture repairs the CRC after changing ELF bytes, allowing the altered image to reach signature verification.

The guest harness in `tests/boot/run-pkg-test.sh` checks extraction reporting by looking for `PKG_EXTRACTED`. The extraction assertion reads that marker from the output.

## Limitations

- The published development seed lets every repository reader produce signatures accepted under `logitos-dev`. Retaining that root while adding another preserves this signing authority (`tools/pkgroots/DEV-SIGNING-KEY.txt`).
- AEX uses a “log but allow” policy: all four signature statuses permit loading when the other container and ELF checks succeed. A malformed signature-record length still causes structural rejection (`c/kernel/exec/load/aex.c`).
- AEX signatures authenticate the ELF length and digest. Container headers and metadata fall outside the signed message (`c/crypto/trust/aexsig.c`).
- Package root changes require regeneration and rebuilding. The package format has no expiry or revocation fields, and the verifier supplies no dependency resolution or installation policy (`c/crypto/trust/pkgsig.h`).
- The guest verifier reads at most 1 MiB and stops at that limit without checking for further input. Package verification accepts trailing bytes beyond the declared payload and returns a view excluding them (`c/apps/coreutils/pkgverify.c`, `tests/unit/pkg_test.c`).
- The advertised `--extract <dst> <file.lpk>` form selects the package input path as its output path too. After successful verification, extraction can overwrite the package file (`c/apps/coreutils/pkgverify.c`).
- Polaris pins establish integrity against the vendored snapshot; vendor signature verification is absent (`c/drivers/gpu/amd/polaris/resource/files.h`).
- Both host signers receive seeds through process arguments. Their comments identify this interface as development tooling and warn against using it for private signing keys (`tools/lpk.c`, `tools/aexsign.c`).
- The cryptographic implementation is experimental and awaits an external cryptographic audit. `TRANSPARENCY.md` and `SECURITY.md` define the project’s security scope.
